# 工程原则

用于需求、架构、实现、测试、调试和代码审查。只采用当前任务需要的部分。

## 选择开发路径

- Bug、测试失败、性能回退和小型重构：直接诊断，不制作产品原型。
- 已有明确目标、范围、Issue 或用户要求直接执行：直接实现，不重复确认。
- 新产品、重要交互或真正缺少业务选择的架构调整：先把关键选择做成便宜、可反应的原型或规格；只有界面判断确实重要时才制作 UI 原型。
- Skill 的创建、归类和迭代：交给 `agent-skill-evolution-workflow` 主持。

先从仓库、代码、文档和运行环境发现事实。只有无法发现、且不同答案会显著改变结果的问题才询问用户。

## 第一性原理推导

AI 会顺着问题里暗含的方案继续回答；在设计复杂功能、选择架构或诊断反复故障前，先检查“这个问题本该这样定义吗”。

1. 把请求改写成用户可观察结果、系统不变量和不可绕过的约束。
2. 沿真实数据流和调用链拆到底层机制，列出输入、状态、依赖、失败边界和必需成本。
3. 区分物理、协议、法规与业务上必须存在的部分，以及历史惯例、旧实现和提问措辞带入的假设。
4. 从必要部分重新推导最小可靠方案，再与现成方案比较；只有证据支持时才保留惯例。
5. 对 Bug 继续追问“什么共享机制允许它再次发生”，在共同根因处修复，并检查兄弟路径。

第一性原理不是要求每次推倒重写。简单、低风险且根因清楚的改动直接完成；若重新推导没有改变决策，不制造新架构。

## 最小正确实现

按以下顺序停止在第一种可靠方案：

1. 不需要存在的能力不做。
2. 复用仓库已有实现和数据结构。
3. 使用标准库。
4. 使用平台或框架原生能力。
5. 使用已安装依赖。
6. 写一行或一个小函数。
7. 最后才增加新模块或依赖。

理解完整调用链后再追求最小 diff。修复共享根因优于给每个调用方添加 guard；删除特殊情况优于堆分支。不得简化掉输入校验、数据保护、安全和明确授权。

## 模块与架构

设计深模块：让调用方只学习小接口，把复杂行为集中在实现内部。

- 接口包含类型、前置条件、不变量、错误模式、配置和性能约束。
- 删除测试：假设删掉模块；如果复杂度分散回许多调用方，它在提供杠杆和局部性；如果复杂度消失，它只是中间人。
- 一个适配器通常是假想扩展；出现两个真实适配器后再引入稳定接缝。
- 测试和调用方使用同一接口；经常绕过接口测试内部实现，通常说明模块边界不对。
- 接收依赖、返回结果；不要在深处偷偷创建依赖或把可计算结果变成隐蔽副作用。

避免只有一个实现的接口、为未来预留的工厂、重复 switch、数据泥团、长消息链和散弹式修改。

## 规格与 Issue

规格至少写清：

- 用户面对的问题和可观察结果；
- 当前基线、范围和不做什么；
- 公共接口、数据和兼容性变化；
- 验收方式、风险和回滚；
- 已确定的实现与测试决策。

需要多个 Issue 时按端到端行为做纵向切片，不按“先数据库、再后端、再前端”做水平切片。每个 Issue 应独立交付一个用户可观察结果，并标出真实阻塞关系。

## 实现与测试

- 从最高且稳定的接口测试行为，不测试私有方法或内部调用次数。
- 适合 TDD 时使用纵向 tracer bullet：一个可失败测试 → 最小实现 → 下一切片。
- 先看测试能否因目标 Bug 或需求缺失而失败；永远为绿的测试没有证明力。
- 期望值来自规格、已知样例或独立事实，不在断言里重新实现同一算法。
- 开发中运行最窄相关检查；完成时运行受影响测试、类型检查、构建或项目既有完整检查。
- 非平凡解析、状态、金额、安全和持久化逻辑至少留下一个可运行回归检查。

## 调试

先建立反馈环，再建立理论。

在展示、保存或共享调试命令、输出、日志、trace、抓包和复现材料前，将密钥、token、
密码、个人身份信息和业务敏感值替换为 `<REDACTED>`。反馈环从环境变量读取凭据，不把
凭据复制进命令、fixture 或报告；捕获材料只保留能证明假设的信号行。

1. 找到一条能捕获用户精确症状的命令：失败测试、CLI、HTTP 探针、浏览器脚本、trace replay 或最小 harness。
2. 让它可变红、确定、快速并可由 Agent 重复运行。
3. 最小化复现；每次删除一个输入、依赖或步骤，保留所有真正负载条件。
4. 列出少量可证伪假设；每个假设说明改变什么会让故障消失或加剧。
5. 一次只验证一个变量，在能区分假设的边界加短期仪表。
6. 在共享根因修复，再让同一反馈环变绿并运行兄弟路径检查。
7. 清理临时日志和探针，把最小复现保留为回归测试。

无法建立反馈环时列出已尝试的方式和缺少的日志、trace、环境访问或生产仪表，不用猜测冒充根因。

## 代码审查

先固定比较点和非空 diff，再沿两条轴分别审查：

1. **规格轴**：遗漏、部分实现、错误实现和未经要求的范围扩张。
2. **标准轴**：仓库规范、正确性、安全、兼容性、数据丢失、测试、文档和代码坏味道。

发现按严重度排序，给精确文件与行号，说明触发条件和影响。没有可操作问题时明确说没有发现，不用风格偏好凑数量。

## 对抗式审查

功能按正常路径通过后，做一次与实现心态分离的破坏性复核。目标不是证明它能工作，而是找到能让它失效、重复执行、泄露、丢数据或无法恢复的输入和时序。

- 从最高稳定接口攻击正常假设：缺失、空值、超长、畸形和越权输入。
- 覆盖边界状态：零、上限、过期、重复提交、并发竞争和乱序事件。
- 注入运行故障：超时、断网、依赖失败、部分成功、进程重启、重试和回滚；检查幂等性、原子性与恢复路径。
- 检查信任边界、资源限制、敏感数据暴露和错误信息；高风险改动继续走安全审查，不以本节替代安全扫描。
- 把能复现真实风险的最小攻击保留为回归检查，修复后重跑正常路径、攻击路径和受影响兄弟路径。
- 按影响与可复现性报告发现；没有可操作问题时明确说明已覆盖的攻击面，不凑数量。

多 Agent 可以提高独立性，但不是完成对抗式审查的前提；只有用户明确授权多 Agent 协作时才启动，否则由当前 Agent 在独立审查阶段完成。

## 研究与文档

- 技术事实优先官方文档、标准、源代码和第一方 API；每个关键结论链接到拥有该事实的主来源。
- 只有领域词汇经常混淆时才维护简短 `CONTEXT.md`；它只保存业务概念和关系，不保存实现细节。
- 只有长期、非显然、会影响后续设计的决定才写 ADR。
- 文件、模块、接口、数据流或运行方式改变时，同步仓库已有架构文档；不为小修复制造一套新文档体系。
